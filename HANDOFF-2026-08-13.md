## Problems solved today (in order)

### 1. TorchDynamo crash (FIXED — in v4+)
**Symptom:** Every worker crashed immediately on startup with:
```
torch._dynamo.exc.Unsupported: Unsupported method call
  Dynamo does not know how to trace method `symmetric_difference` of class `type`
```
**Cause:** PyTorch 2.8's JIT compiler (TorchDynamo) tries to trace `einops.rearrange` during VoxCPM2's warmup inference. `einops` uses `set.symmetric_difference` which dynamo can't trace.

**Fix:** Added to the top of `main.py` (before the voxcpm import):
```python
import torch
torch._dynamo.config.disable = True
```

**Note:** The env var `TORCHDYNAMO_DISABLE=1` in RunPod settings did NOT work — it has to be set in code before torch is used.

---

### 2. Disk space fitness check failure (FIXED — 20GB container disk)
**Symptom:** Worker loaded VoxCPM2 successfully (`VoxCPM2 ready`) but then RunPod's fitness checker killed it:
```
Fitness check failed: _disk_check | RuntimeError: Insufficient...
Worker is unhealthy, exiting.
```
**Cause:** Default container disk was 5GB. VoxCPM2 model + packages filled it up.

**Fix:** In RunPod → Edit endpoint → Docker configuration → **Container Disk set to 20GB**.

---

### 3. Cloudflare Worker timing out (FIXED — polling approach)
**Symptom:** `/tts` requests returned `{"error":"TTS failed","detail":{"status":"IN_QUEUE"}}` or timeout errors.

**Cause:** The original code used `/runsync` which has a 30-second max. VoxCPM2 cold start takes 3-5 minutes, and even warm jobs take longer than 30 seconds sometimes.

**Fix:** Rewrote the `/tts` route in the Cloudflare Worker to:
1. Submit job with `/run` (async)
2. Poll `/status/{id}` every 5 seconds for up to 90 seconds
3. Return WAV audio bytes when `status === 'COMPLETED'`

Current Worker code is already deployed at `em1-prayer.kayuso2011.workers.dev`.

---

### 4. Wrong audio pitch/speed — sample rate mismatch (PARTIALLY FIXED — v7 ready to deploy)
**Symptom:** Audio came through but was very deep and slow (like a slowed-down recording). Duration was ~13-17 seconds for a short sentence.

**Cause:** `model.tts_model.sample_rate` returns `16000`, but the model actually outputs audio at **48000 Hz**. We were writing the WAV file with the wrong sample rate in the header, so players played it back 3x too slow.

**Evidence from logs:**
```
wav shape: (168960,), dtype: float32, reported sr: 16000
```
168960 samples ÷ ~3.5 seconds of speech = **48000 Hz** true rate.

**Fix prepared (v7):** `main.py` already updated to hardcode `output_sr = 48000`. Just needs to be built and deployed.

## Current state of files

### `voice-server/main.py` — READY, not yet deployed as v7
```python
import io, base64, runpod, torch
torch._dynamo.config.disable = True  # must be before voxcpm import
from voxcpm import VoxCPM
import soundfile as sf

print("Loading VoxCPM2…")
model = VoxCPM.from_pretrained("openbmb/VoxCPM2", load_denoiser=False)
print(f"VoxCPM2 ready — sample rate: {model.tts_model.sample_rate} Hz")

def handler(job):
    job_input = job.get("input", {})
    text = job_input.get("text", "").strip()
    if not text:
        return {"error": "No text provided"}
    try:
        wav = model.generate(text=text, cfg_value=2.0, inference_timesteps=10)
        buf = io.BytesIO()
        output_sr = 48000  # true output rate (model lies and says 16000)
        sf.write(buf, wav, output_sr, format="WAV")
        audio_b64 = base64.b64encode(buf.getvalue()).decode("utf-8")
        return {"audio": audio_b64, "sample_rate": output_sr}
    except Exception as e:
        return {"error": str(e)}

runpod.serverless.start({"handler": handler})
```
